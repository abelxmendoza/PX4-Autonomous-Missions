BUG-009

Scenario:
This machine runs multiple concurrent Claude Code sessions against the
same shared repo checkout, each occasionally launching its own SITL
simulation for verification. `scripts/run_demo.sh` and
`scripts/run_full_stack.sh` clean up their launched processes on exit
via a shared `_stack_cleanup.sh` helper.

Requirement violated:
N/A — this is a test-infrastructure bug, not a flight-behavior
requirement. It matters because it made the test process itself
actively harmful to concurrent work on shared infrastructure.

Symptom:
Confirmed live: one session's demo cleanup took down another active
session's simulation as collateral damage.

Expected behavior:
Shutting down one launch's processes must not affect any other,
unrelated simulation running concurrently on the same machine.

Actual behavior:
Cleanup used `pkill -f <pattern>` against process-name patterns like
"gz sim" or "px4" — patterns that match *any* process with that name,
regardless of which launch started it. On a shared box with more than
one simulation running, this killed the other session's identically-named
processes too.

Root cause:
Pattern-based process matching has no notion of "which launch owns this
process" — it can only match on command-line text, which is identical
across independent simulation instances.

Fix:
Replaced pattern-based cleanup with a PID-scoped approach: snapshot the
launch tree's exact descendant PIDs before sending any shutdown signal
(so orphaning hasn't happened yet), and kill only those specific PIDs.

Two follow-on bugs were found and fixed during validation of this fix
itself:
- The snapshot function crashed the whole script under `pipefail`
  whenever `gz sim` (which detaches from the process tree almost
  immediately) hadn't spawned yet at snapshot time — needed a separate
  before/after PID diff to catch it at all.
- A `TimerAction`-delayed child process spawning during the shutdown
  grace period could still slip through a single point-in-time
  snapshot. The grace period is now bounded at 30 seconds (past the
  launch file's longest `TimerAction` delay), with a second PID capture
  taken after it.

Regression test added:
None — this is shell-script process-management behavior, not something
covered by the Python test suite. Verified live by confirming a
cleanup no longer affects a concurrently running, independently
launched simulation.
