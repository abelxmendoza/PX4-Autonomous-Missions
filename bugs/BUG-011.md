BUG-011

Scenario:
Bringing up a new forward-facing Gazebo camera sensor on a development
machine with both an NVIDIA discrete GPU and an unsupported Intel
integrated GPU.

Requirement violated:
N/A — simulation-host configuration bug, not a flight-behavior
requirement. Relevant to any requirement that depends on
rendering-based sensors (camera, and potentially LiDAR under different
conditions) actually producing data.

Symptom:
The new camera topic published, but no actual image data could be
confirmed coming through — rendering-based sensors were suspected to be
silently producing nothing on this machine.

Expected behavior:
`gz-sim` in headless mode should select a working GPU for its EGL
rendering context.

Actual behavior:
`gz-sim`'s headless EGL device enumeration picked the unsupported Intel
integrated GPU instead of the NVIDIA discrete one. Mesa emitted a
warning but did not fail fatally, so the failure mode was silent —
every rendering-based sensor would produce nothing with no obvious
error pointing at the cause.

Root cause:
Headless EGL device enumeration order isn't guaranteed to prefer the
capable GPU on a multi-GPU machine, and an unsupported device failing
"softly" (warning, not error) makes this class of bug easy to miss.

Fix:
Force the NVIDIA EGL vendor ICD when present in the launch
configuration (`full_stack.launch.py`); no-op on single-GPU machines.

Regression test added:
None — host GPU configuration isn't something a unit test can exercise
portably. Documented as a known partially-open item: the camera topic
was confirmed live with a real publisher against this fix, but full
end-to-end frame verification (actually pulling and inspecting a
rendered frame) was still open at the time of this fix and deliberately
not chased further, rather than sinking additional live-SITL debugging
time into it immediately.
