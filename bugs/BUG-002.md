BUG-002

Scenario:
SITL flights immediately after BUG-001's plugin fix landed.

Requirement violated:
N/A — predates the V&V harness. Same underlying precondition as
BUG-001: PX4 must see barometer/magnetometer data.

Symptom:
Barometer and magnetometer topics (`sensor_baro`, `sensor_mag`) still
never published on uORB, even though the world SDF now explicitly
declared the `AirPressure` and `Magnetometer` plugins added in BUG-001.

Expected behavior:
Declaring the plugins once, at world scope, is sufficient for Gazebo to
simulate and publish both sensors.

Actual behavior:
The sensors still silently produced nothing.

Root cause:
PX4's own launch tooling sets `GZ_SIM_SERVER_CONFIG_PATH` to a
`server.config` that injects the same system plugins into every world
automatically, targeting `entity_name="*"`. With the world SDF *also*
declaring `AirPressure`/`Magnetometer` (added in BUG-001) plus the
pre-existing `Imu`/`NavSat`, every one of these plugins was now
registered twice. The duplicate registration silently prevented Gazebo
from wiring the model-path sensor topics correctly — Mesa/Gazebo gave
no fatal error, so the failure was invisible except as "no sensor data."
The actual sensor names in `x500_base/model.sdf`
(`air_pressure_sensor`, `magnetometer_sensor`, matching PX4's
`GZBridge.cpp`) were already correct and needed no changes.

Fix:
Removed all `<plugin>` declarations from `worlds/obstacle_world.sdf`
entirely — including the ones added in BUG-001 — since PX4's own
server-config injection already provides them. The world file now
contains only scene, spherical_coordinates, physics, light, ground
plane, and obstacle models.

Regression test added:
None — Gazebo/PX4 launch-configuration interaction, not unit-testable
in isolation. Verified by confirming `sensor_baro`/`sensor_mag` topics
published in a live SITL run.

Commit: bfb6f90

Note: BUG-001 and BUG-002 are two chapters of the same underlying
problem, twenty minutes apart — the first fix (add the plugins) was
locally correct but didn't account for PX4's own plugin injection, so
it traded a missing-plugin failure for a duplicate-plugin failure with
an identical symptom. Left here as two entries because the root causes
are genuinely different and the second was only found by looking one
layer deeper at how PX4 actually launches Gazebo worlds.
