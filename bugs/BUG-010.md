BUG-010

Scenario:
Reviewing the GPS-denied-zone feature ("Pass 1"): a deny-inject flight
that should trigger `LocalizationStateMachine`'s `LOC_FAILSAFE` event and
a corresponding hold/land response.

Requirement violated:
REQ-GPS-POLICY-01 (localization failsafe shall reach a terminal or hold
state) — not violated in the vehicle's actual behavior, but the
requirement's own verification was silently defeated.

Symptom:
`LOC_FAILSAFE` never appeared in any CSV row, even on flights where it
genuinely occurred. Because `REQ-GPS-POLICY-01`'s check has a "no
events seen" early-out (correctly, so it doesn't fail when a scenario
never exercises localization failsafe at all), the requirement always
reported PASS — including on the exact deny-inject → hold/land case it
exists specifically to verify. A verification requirement that always
passes, even in the scenario it's meant to catch, gives false
confidence that is arguably worse than no check at all.

Expected behavior:
Every `LOC_FAILSAFE` event the localization state machine produces
should appear in the flight log's `loc_event` column so
REQ-GPS-POLICY-01 can actually evaluate the hold/land response that
followed it.

Actual behavior:
`_control_loop` returned early past every code path that calls
`_log_row` the moment it observed `loc.failsafe` — and the event field
is one-shot (sticky back to `None` on the very next tick) — so no CSV
row was ever written while the event was still set. It fired and
vanished within the same tick, invisible to the log.

Root cause:
An ordering bug: the localization failsafe branch handled the failsafe
transition and returned before reaching the logging call, instead of
logging the current tick (including the one-shot event) first and only
then acting on it.

Fix:
Reordered the control loop so `_log_row` is called before any
failsafe-transition return, guaranteeing a one-shot event is captured
in at least one CSV row before it resets. (This underlying flight-code
fix landed via a concurrent session sharing this working tree; the
regression test below was authored separately, end-to-end, against the
already-fixed code.)

Regression test added:
`test_offboard_mission_node.py::test_gps_denied_failsafe_event_is_captured_in_the_log`
— drives the real control loop end-to-end (not just the pure
`LocalizationStateMachine`) and reads the actual CSV back to confirm
`loc_event == "LOC_FAILSAFE"` is captured. Verified it fails without the
fix (temporarily reverted it, confirmed the assertion caught the bug,
restored it) before committing.
