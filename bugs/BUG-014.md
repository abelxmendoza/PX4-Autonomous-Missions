BUG-014

Scenario:
Live SITL flight (`waypoints` mode) with `obstacle_source=sensor_only`
(the configuration `scripts/run_demo.sh` actually uses by default —
see the investigation note below), passing near a tight corridor with
more than one physical obstacle.

Requirement violated:
REQ-CLEARANCE-01 (no mapped-obstacle intersection) in spirit — this is
a near-collision found via real position/LiDAR telemetry, even though
`sensor_only` mode by definition has no mapped-obstacle geometry for
the formal checker to compare against.

Symptom:
LiDAR showed front/left/right ranges all under 1m simultaneously.
Position telemetry showed jumps of 5-9m within 2-3 seconds and negative
altitude readings — signatures consistent with an actual Gazebo physics
collision, not merely a bad setpoint.

Expected behavior:
When a blind, map-free bypass is underway and live LiDAR reveals a
second, closer obstacle that the original plan had no way to know
about, the mission logic should abandon the stale plan and replan from
current sensor evidence — not rigidly stream the original target
regardless of what the sensors now show.

Actual behavior:
The sensor-only bypass path computes its target once, from whatever the
sensor showed at the moment the maneuver started (correctly "locked," by
design, so it doesn't thrash on ordinary sensor noise) — but then
streamed that target unconditionally for the rest of the maneuver, with
no mechanism to notice a *second*, unanticipated obstacle appearing
mid-maneuver.

Root cause investigation note: the first hypothesis investigated was
that this was the same class of bug as BUG-012 (a "should have been
locked, wasn't" oscillation). That turned out to be wrong and was
corrected mid-investigation before being reported as fixed: `run_demo.sh`
hardcodes `avoidance_strategy=climb` *and* `obstacle_source=sensor_only`,
and `_apply_avoidance`'s top-level branch routes *all* avoidance through
the sidestep/bypass path whenever `obstacle_source == "sensor_only"`,
regardless of `avoidance_strategy`. Every `run_demo.sh` flight was
therefore exercising the sidestep/bypass branch the whole time, never
the climb branch BUG-012 fixed — an improvement seen in an earlier
verification run was very likely run-to-run variance, not that fix
actually applying here.

Root cause (actual): the sensor-only bypass branch had no mechanism at
all to detect a second obstacle appearing after the bypass target was
already committed.

Fix:
Added an emergency-replan check at the top of the sensor-only bypass
branch: if a bypass is active, no obstacle-map object backs it
(`_bypass_obstacle is None`, i.e. it's a blind sensor-only plan), and a
live sensor reading is closer than `planner_emergency_range_m`, drop the
stale plan (`_bypass_target`, `_sensor_advance_target`,
`_sensor_leg_origin`, `_sensor_leg_target` all reset to `None`) and let
it be recomputed from current position and current sensor evidence.

Regression test added:
`test_offboard_mission_node.py::test_sensor_only_bypass_replans_on_emergency_close_reading`
— establishes a bypass with clear sensors, then moves the vehicle and
introduces a close reading on a side the original plan never saw,
asserting the bypass target changes. Verified it fails without the fix
(temporarily disabled the check, confirmed the assertion caught the
stale target, restored it) before committing.

See BUG-015 for a second, distinct bug this fix itself introduced.
