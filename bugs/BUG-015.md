BUG-015

Scenario:
Live SITL flight verifying the BUG-014 fix itself
(`HEADLESS=1 ./scripts/run_demo.sh waypoints`), before that fix was
considered done.

Requirement violated:
No formal REQ-ID directly; this is a mission-progress/liveness failure
introduced by BUG-014's own fix, ultimately surfacing as a
REQ-GEOFENCE-01 breach as a side effect.

Symptom:
The mission got permanently stuck at waypoint 3 of 9 for the entire
flight. The log showed dozens of "AVOID emergency replan" events firing
within a span of seconds, altitude climbing into the 12m ceiling, a
geofence breach, and a FAILSAFE landing — objectively worse than the
near-collision behavior BUG-014 was fixing.

Expected behavior:
A blind sensor-only bypass, by design, executes close to the obstacle
it's sidestepping — that proximity is expected and should not itself be
treated as a new threat.

Actual behavior:
BUG-014's emergency-replan check triggered on *any* live sensor reading
under `planner_emergency_range_m`, with no distinction between "this is
the same obstacle we're already correctly bypassing, and closeness is
expected" and "a genuinely new, closer threat has appeared." Since
`_bypass_obstacle` is always `None` for every sensor-only bypass (there
is no obstacle-map object to reference), being close to the *intended*
obstacle re-triggered the same check every tick: the plan was
continuously torn down and immediately rebuilt from the still-close
reading, so the vehicle never got the chance to actually move away
before the next tick discarded the new plan too. Confirmed directly in
SITL logs: "BYPASS created" firing on nearly every control tick for
several seconds straight.

Root cause:
The trigger condition compared a live sensor reading only against an
absolute threshold (`planner_emergency_range_m`), with no reference to
what the reading was *when the current plan was made*. Any proximity
below that threshold looked identical to the check, whether it was the
obstacle already being deliberately bypassed or a brand-new one.

Fix:
Snapshot the closest valid sensor reading at the moment a sensor-only
bypass target is created (`_bypass_sensor_ref`). Only tear up the plan
when a live reading is now *measurably closer than that reference*
(more than 0.4m closer) — a genuine new threat — rather than merely
being close in absolute terms. Also added a 2-second cooldown
(`emergency_replan_cooldown_s`) between emergency replans as a second,
independent guard against rapid re-triggering.

Regression test added:
`test_offboard_mission_node.py::test_sensor_only_bypass_does_not_thrash_on_expected_proximity`
— establishes a bypass with a close-from-the-start sensor reading (by
design, as in a real close sidestep), then advances the vehicle
slightly on each of several subsequent ticks with the *same* close
reading, and asserts the bypass target is never rebuilt. The first
version of this test used a fixed vehicle position across all ticks and
passed even with the bug present — with identical inputs, a torn-down
and rebuilt target recomputes to the same numeric value, hiding the
thrash. Fixed by moving the vehicle slightly between ticks (as it
would in real flight), so a spurious rebuild produces a detectably
different target. Verified the corrected test fails without the fix
(confirmed via captured log output showing "BYPASS created" on every
tick and a numerically different target after 5 ticks), and passes with
it restored.

Commit: 662b72e (bundled with BUG-013 and BUG-014)

Note: this is a bug introduced by fixing another bug (BUG-014), caught
by re-running the exact same live SITL verification step used to check
that fix, before it was ever committed or reported as done. The lesson
generalized here: fixing a "rigid, never replans" failure by adding an
"always replan on proximity" check just traded one failure mode for its
opposite (thrashing) — the correct fix needed a *relative* signal
(getting closer than expected), not an absolute one.
