BUG-017

Scenario:
Bringing up the stereo camera pair (`models/mono_cam_right` alongside PX4's
stock `mono_cam`) for visual odometry. Reproduced on the original single
camera too: no camera image topic ever delivered a frame in any headless or
windowed SITL run.

Requirement violated:
None existed for camera data at the time. This is the gap BUG-011 recorded as
"no actual rendered frame has been pulled yet" -- every consumer of the camera
(`vision_marker_node`, then the stereo odometry) had been reading a topic that
was advertised but never published.

Symptom:
- `ros2 topic hz` on both bridged image topics: no messages, ever.
- `gz topic -l` lists the image and camera_info topics (the sensor exists and
  is advertised); `gz topic -e -t <image topic>` and the `camera_info` topic
  (pure metadata, no rendering) also produced nothing.
- `camera_bridge` logged `subscribed=True` the whole time, so nothing in the
  logs pointed at the problem.
- GPU LiDAR on the same vehicle worked throughout.

Expected behavior:
A camera sensor declared in the SDF with `always_on=1` and `update_rate=30`
publishes frames to its gz-transport topic once the server is running.

Actual behavior:
The sensor was created (Ogre2 render context and `Ogre2Camera` objects
initialized, "Enabling camera sensor" logged) but never produced a frame.

Root cause:
Gazebo camera sensors only render while a subscriber is registered with their
publisher (GPU LiDAR publishes regardless, which is why LiDAR worked all
along). PX4's startup runs the Gazebo server with `GZ_IP=127.0.0.1`.
gz-transport only registers a subscriber with a publisher when both sit on the
same interface, so every camera consumer started *without* `GZ_IP`
(`camera_bridge`, the C++ wake-up subscriber, `gz topic -e`) subscribed
"successfully", received nothing, and never woke the sensor.

Verified live on one running stack, same binary, same minute: started with
`GZ_IP=127.0.0.1` it received ~10 frames/s per camera; started without it,
0 frames. `gz topic -i` likewise lists a subscriber only when `GZ_IP` matches.
That also explains the observation recorded in the first draft of this entry
(`gz topic -e` staying silent): it ran without `GZ_IP` too.

What was ruled out first, in order (each cost a full SITL boot): missing
`model.config` for the new model (a real, separate bug, fixed); topic-name
mismatch (LiDAR uses the identical leading-slash pattern and works);
`GstCameraSystem` consuming frames (it is just another subscriber -- verified
in its source); headless vs windowed (same result); NVIDIA/EGL driver
(`LIBGL_ALWAYS_SOFTWARE=1` changed nothing); Ogre 1 instead of Ogre 2
(`config/gz_server_ogre.config`, a dead end -- the engine was never the
problem); subscribing before vs after the sensors exist (no difference).
Two explanations offered earlier in this repo's history -- that the Python
gz-transport bindings never register as connections, and that nested
(include-merged) camera models never emit frames -- do not account for the dark
cameras seen here: the committed model already defines the cameras as
first-class links, and the cameras stayed dark until `GZ_IP` matched.

Fix:
`full_stack.launch.py` starts every camera consumer with
`GZ_IP=127.0.0.1` (`GZ_SIM_ENV`): the two `camera_bridge` instances and
`scripts/gz_cam_sub.cpp`. The C++ subscriber now also waits for each topic's
publisher and re-subscribes a silent topic, so start-up order cannot strand
it. Anything else that wants camera frames from a PX4-launched Gazebo must set
the same `GZ_IP`.

Regression test added:
No unit test (Gazebo/transport runtime behavior). Guarded by the live validation
run: its flight log records `vo_healthy`, and a run in which the cameras go dark
shows 0% availability and fails REQ-VO-AVAIL-01 (`check_vo_availability`, with
`test_vo_availability_fails_when_the_cameras_go_dark` encoding exactly that
signature).
