The Verification Log

I built a drone that flies itself and dodges obstacles on its own — then spent just as much effort proving it actually works, the way you'd have to before trusting it with anything real. That process caught six real problems a working demo alone would never have shown.

N01

What I built

A simulated drone that flies a mission on its own — no joystick, no remote pilot. It uses a live sensor (not a pre-loaded map) to spot obstacles and steer around them in real time. If it loses GPS partway through the flight, it automatically switches to a backup way of tracking where it is. And if it ever strays outside its allowed area, runs low on battery, or loses signal, it recognizes that and lands safely instead of continuing on blind.

N02

Why I didn't just trust the demo

A demo only proves a system can look right once. It says nothing about the other ninety-nine times.

So instead of watching it fly and calling it done, I recorded every detail of each flight and checked that recording against a list of specific rules it has to follow — like a safety inspection, run automatically after every single flight. Did it stay in bounds? Did it actually use sensor data before every turn? Did the backup navigation stay active the whole time GPS was out? Every rule gets a plain pass or fail, and the check runs on its own — I don't have to remember to do it.

This process is what actually found the six issues below — not a code review, and not "it looked fine when I watched it." It stops and flags a failure the moment any required safety rule is broken.

N03

Six real problems this caught

Every one of these looked completely fine during a normal test flight. Each only surfaced because I checked it against a specific rule instead of trusting that "it flew fine" meant "it's correct."

FINDING-01 Obstacle avoidance

A safe flight path was wrongly flagged as a crash

When the drone flew in a straight line right alongside an obstacle — not into it — the collision check sometimes mistakenly counted that as a hit, which would force an unnecessary detour around something it was never actually going to touch.

Why it matteredA safety check that cries wolf on a genuinely safe path teaches you to stop trusting it — more dangerous than not having the check at all.
FINDING-02 Sensor logic

"All clear" was being read as "no data"

The obstacle sensor has a specific signal that means "I checked this direction, it's genuinely clear." My safety checklist was mistakenly treating that exact signal as if the sensor hadn't reported anything at all — so steering toward the direction confirmed safest got flagged as unverified.

Why it matteredSame problem as above: a check that penalizes the right answer undermines trust in the whole safety system.
FINDING-03 Flight logging

The most important safety event wasn't being recorded

At the exact moment the drone triggered its GPS-loss safety response, the logging code exited early — before it wrote that event down. So the one moment that most needed a record of "here's why the drone reacted" simply wasn't in the log.

I confirmed this was a real, catchable bug by deliberately re-breaking it, watching my test correctly fail, then fixing it again — not just writing a test that happened to pass.

Why it matteredA safety response that isn't logged is indistinguishable from one that never happened, if anyone ever needs to review what the drone actually did.
FINDING-04 Failsafe handling

Two different emergencies, but only one setting was being checked

The drone has separate settings for "what to do if I leave my boundary" versus "what to do if I lose GPS" — but the code was checking the boundary setting for both. A GPS emergency was silently following the wrong rule.

Why it matteredA setting configured for one type of failure was quietly controlling a completely different one — the kind of bug that only shows up once both failures happen for real.
FINDING-05 GPS backup system

The GPS backup had never actually been tested against a wrong answer

The simulated backup positioning system was quietly reading the drone's exact, perfect position and reporting that as its own reading — meaning it could never be wrong. So the entire "what happens when GPS goes out" scenario had never really been tested against realistic, imperfect backup data.

I rebuilt it to include realistic drift and error, the way an actual backup sensor behaves.

Why it matteredThis wasn't something broken — it was a safety feature that had never really been put to the test. Looking safe and being tested are two different things.
FINDING-06 Automated testing setup

Three safety tests existed but were never actually being run

I had written three test files that needed no special setup to run — but they'd never been wired into the automatic testing process. They could have silently broken and nobody would have known.

Why it matteredA test that exists but never runs gives false confidence. It looks like coverage from the outside while providing none.
N04

What I'm still finishing

I'd rather be upfront about what isn't done than round up. I built and tested a camera-based marker detector — it correctly recognizes markers in isolated tests — but I haven't yet confirmed it working live, end-to-end, inside the full simulator.

A real hardware quirk I found along the way

Trying to test it live surfaced a separate, genuine problem: on a laptop with two graphics cards, the simulator's rendering was silently defaulting to the wrong, weaker one and producing no camera image at all. I tracked that down and fixed the underlying configuration.

Even after that fix, I haven't yet gotten a confirmed live image from the camera in that environment, even though a different sensor on the same drone works instantly — so there's one more specific issue left to track down.

The detector itself is built and tested. The only thing I won't claim is a live camera result I haven't personally seen work.
