N01

A GPS-denied autonomy stack, briefly

The vehicle is a simulated x500 quad flying real PX4 offboard control — not a scripted trajectory. A mission executive tracks battery, link quality, and propellant against a resource budget and can degrade the mission before a hard failure forces it to. A LiDAR-backed avoidance layer only ever reacts to live sensor evidence, never to a known map, so a demo can't quietly cheat.

N02

Verification, not vibes

A demo proves a system can look right once. It says nothing about the other ninety-nine runs.

So every simulated flight gets logged to CSV — state, position, target, sensor evidence, fence status, GPS-denial phase — and a harness replays that log against a table of named requirements: REQ-STATE-01, REQ-GEOFENCE-01, REQ-AVOID-SENSOR-01, and eleven others, each with a severity (MUST or SHOULD) and a plain-English description. The web replay renders the same verdicts next to the flight itself, so a requirement and the exact moment it passed or failed sit on the same screen.

RequirementChecksSample verdict
REQ-GEOFENCE-01Hard fence breach reaches FAILSAFE within the response windowPASS
REQ-AVOID-SENSOR-01Every avoidance call has fresh LiDAR evidence behind itPASS
REQ-VIO-FUSION-01External vision stays fused for the entire GPS-denied windowPASS

This is what actually found the bugs below — not code review, not a demo that happened to work. A CLI called vv_replay exits non-zero the moment any MUST requirement fails, so it also runs unattended in CI against committed recordings.

N03

Six bugs a working demo hid

Each of these flew fine in the simulator. Every one only surfaced once a log got replayed against a specific, named claim about what "fine" means.

FINDING-01 mission_logic.py · segment_hits_expanded_aabb

A path running parallel to an obstacle registered as a hit

The collision check is a Liang-Barsky slab test over two axes. When a path segment ran exactly parallel to one axis of an obstacle's box — dx or dy effectively zero — the loop fell through into computing a bogus intersection distance instead of returning "no hit."

# before: falls through to a bogus hit
if abs(dist) < 1e-12:
    break

# after: parallel + outside the slab genuinely can't hit
if abs(dist) < 1e-12:
    if p0 < minimum or p0 > maximum:
        return False, dist_start, n0, e0
    continue
Why it matteredA straight leg running alongside — not into — an obstacle could get flagged as a collision, which either forces an unnecessary reroute or, worse, teaches you to distrust a correct route.
FINDING-02 vv_harness.py · check_sensor_backed_avoidance

"Confirmed clear" was mistaken for "no data"

The LiDAR sector publisher uses -1.0 to mean "I checked this direction and there's nothing there" — a fresh, valid, genuinely good reading. The V&V check treated any range < 0.0 as missing evidence, so steering toward the single safest possible direction — a sector confirmed clear — was flagged as unverified.

Why it matteredA safety check that penalizes the correct behavior teaches you to stop trusting the safety check, which is worse than not having one.
FINDING-03 offboard_mission.py · _control_loop

The most safety-relevant event never made it into the log

On the exact tick a GPS-denial failsafe fired, _control_loop returned early — before the line that writes the CSV row. The event is one-shot; it's None on every tick after. The row that should have recorded "this is why we failsafed" simply never existed.

Caught by writing a node-level test that forces the exact conditions, then verified for real: I temporarily reverted the fix and confirmed the new test actually failed before restoring it — proof the test catches the regression, not just that it passes today.

Why it matteredA failsafe that isn't in the log didn't verifiably happen, from an auditor's perspective — indistinguishable from a failsafe that never fired at all.
FINDING-04 offboard_mission.py · FAILSAFE handler

Two failsafe reasons, one parameter checked

The FAILSAFE state handler needs to route differently depending on why it fired — a geofence breach and a GPS-denial event have different configured actions. The handler was reading geofence_action for both cases, so a GPS-denial failsafe silently obeyed the geofence's policy instead of its own.

Why it matteredThe parameter you set for one failure mode quietly governed a different one — the kind of bug that only shows up once both failure modes actually occur in the same flight.
FINDING-05 vio_bridge.py

The GPS backup was never actually tested against error

The simulated visual-odometry source read Gazebo's exact ground-truth pose and republished it as "external vision," with a fixed, sensor-spec covariance that had no relationship to the (zero) actual error in the data. Every GPS-denied flight was backed by a positioning source that literally could not be wrong.

I added a bounded, mean-reverting random walk — real drift, clamped the way a re-anchoring VIO system's error is, plus a covariance that honestly grows with the accumulated bias instead of staying fixed.

Why it matteredThis wasn't a bug that broke something — it was a gap that meant nothing had broken yet. The entire GPS-denial pipeline had never been exercised against a position source that could plausibly disagree with reality.
FINDING-06 .github/workflows/unit-tests.yml

Three test files existed and ran exactly nowhere

test_lidar_sectors.py, test_localization_logic.py, and test_vio_bridge.py — pure Python, no simulator dependency, free to run in any CI job — had simply never been added to the CI invocation. They could regress silently forever.

Why it matteredA test that exists but never runs is a false sense of coverage — worse in a specific way than no test at all, because it looks like safety from the outside.
N04

Where verification hit a wall

Not every claim here is closed out, and I'd rather say so than round up. I added a real forward-facing camera sensor and an OpenCV ArUco marker detector — genuinely unit tested end to end against synthetically generated marker images — but I have not personally confirmed a rendered frame coming out of a live simulator run.

The bug I found trying to verify the bug fix

Attempting to confirm it live surfaced a real, separate problem: on a dual-GPU laptop, Gazebo's headless render pipeline enumerated EGL devices and landed on an unsupported integrated GPU instead of the working discrete one — Mesa warned, didn't crash, and every rendering-based sensor produced nothing. Forcing the NVIDIA EGL vendor ICD fixed that cleanly and is committed.

Even with a clean render context, the camera topic still hasn't produced a confirmed frame in that environment, while the sibling LiDAR sensor on the same vehicle publishes instantly every time — narrowing it to a camera-specific activation question I haven't run down yet.

The detector, the geometry, and the GPU fix are all real and tested. The one thing I won't claim is a rendered frame I haven't personally seen.
