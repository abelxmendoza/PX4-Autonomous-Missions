Test engineering · simulated motor test bench

Before a drone flies, its motors are tested on a bench.
This test runs itself, breaks things on purpose, and grades the result.

A drone motor is clamped to a test bench with sensors that measure how hard it pushes, the battery voltage and the motor temperature. Instead of a person watching gauges, a test script drives the motor through a sequence, deliberately breaks two sensors, and checks five rules automatically. Press play below; the panel explains each moment.

Why this matters

🛠️
Catch problems on the ground

A weak motor or a sagging battery found on a bench costs minutes. Found in the air, it costs a drone. Teams test every motor and battery before they fly.

📟
Sensors fail too

A broken sensor can look exactly like a broken motor. A trustworthy test has to tell the difference, so this one breaks its own sensors on purpose and checks it notices.

✅
Same test, every time

Software runs the sequence and grades the result identically on every run, and keeps the evidence. That is the core of test engineering, and of the tools aerospace and drone companies build for their test stands.

How the test works

Run a throttle sequence

The script asks the motor for 30%, 60%, 90% and 50% power, then switches it off.

Measure everything

Thrust, voltage and temperature are read 20 times a second over Modbus, the standard language industrial measuring equipment speaks.

Break sensors on purpose

The thrust sensor's signal is cut for 2 seconds, and later the temperature sensor freezes.

Grade automatically

Five rules are checked from the recorded data. Each one passes or fails, with no human judgement involved.

What's real, and what's simulated

Real
  • The test automation: the scripted sequence, the fault injection and the five checks.
  • The Modbus server, the same protocol real bench equipment uses, tested over a real network connection.
  • Each check is proven able to fail: tests feed it bad data and confirm it catches it.
Simulated
  • The motor, battery and sensors are a software model with realistic behaviour (spin-up lag, voltage sag, heating), not a physical motor.
  • The numbers are believable but not measured from real hardware.
  • On a real bench, the model is replaced by real sensors; the test script and checks stay the same.
For engineers: model, registers, and requirements

The rig is VirtualTestRig: first-order RPM lag (τ 0.35 s), thrust ∝ RPM², battery sag with load, a thermal climb toward a load-dependent steady state, and Gaussian sensor noise. A background thread steps it at 20 Hz and serves it from a pymodbus Modbus TCP server as seven holding registers (unsigned 16-bit, fixed-point ×100):

RegisterValue
0throttle command % (write)
1RPM
2modelled thrust (N)
3load-cell reading (N)
4battery voltage (V)
5winding temperature (°C)
6active fault code

The recorded campaign is run in-process with a fixed seed so it is reproducible; the Modbus path is covered by its own integration test over real sockets. Requirements REQ-BENCH-001…005 are re-derived from the samples. REQ-BENCH-005 flags a channel whose reading has not changed at all for 0.5 s and requires every injected freeze to be caught within 1 s with no false alarms. This run does not inject a battery brownout, so REQ-BENCH-003 is only checked against normal sag.
